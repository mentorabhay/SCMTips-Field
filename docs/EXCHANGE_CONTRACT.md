# SCMTIPS Field and the SCMTIPS exchange contract (v1)

How SCMTIPS Field plugs into the SCMTIPS core, and how any other system can plug in the same way.
This page is written by hand; the contract itself is generated by the core and kept, unchanged, in
[`docs/integration/exchange-contract-v1/`](integration/exchange-contract-v1/README.md).

Two kinds of interface are involved:

1. **The exchange contract** (`scmtips.exchange/v1`): eight business messages the core trades with
   the systems around it, each with a JSON Schema, an example and an XLSX (and, for single-table
   messages, CSV) template with the same columns. One format, two transports: a live JSON push or
   pull, or a file uploaded in the core.
2. **The core's own app APIs** that Field calls for sign-in, devices and decisions. They are not
   exchange messages, but they are what an approver on the phone or the glasses uses.

Nothing on this page is a secret. Settings are named by their environment variable only; values
live in the owner's git-ignored `.env.local` (see `.env.example` for the names).

| [`goods_receipt`](integration/exchange-contract-v1/schemas/goods_receipt.schema.json) | to the core | I10 | `goods_receipt` | yes | **yes** | A goods receipt posted in the ERP (movement 101) becomes the two rows the contract names, one `inventory` row and one `open_supply` row, pushed to the same two feeds (section 2.4). |

The envelope (`contract`, `message`, `message_id` as the idempotency key, `correlation_id`,
`source_system`, `sent_at`, `simulated`, `rows` or `parts`), the value rules (the core's upper-case
codes, ISO dates, dot decimals) and the signing of live pushes are in the contract's
[README](integration/exchange-contract-v1/README.md); every schema is also in
[`contract.json`](integration/exchange-contract-v1/contract.json), with one example per message in
[`examples/`](integration/exchange-contract-v1/examples/) and the templates in
[`templates/`](integration/exchange-contract-v1/templates/).

**Live goods receipts and ERP extracts travel as feed rows, not as envelopes.** The contract says so
for both legs: live, the ERP pushes its rows to the core's data feeds (`POST
/v1/inbound/feeds/{feed_id}`), one table per feed; the envelope with `message_id` is the file and
validation form of the same rows. Field therefore sends `{"rows": [...]}` bodies to the
`inventory` feed and the `open_supply` feed, with the columns of the contract's `inventory` and
`open_supply` tables.

## 2. How Field uses the core

Every call Field makes to the core carries `X-Requested-With: lr`. Field never stores or logs a
core token, a feed secret or a password.

### 2.1 App sign-in and `/v1/auth/exchange`

1. The Android app signs in at the core: `POST {FIELD_CORE_BASE_URL}/v1/auth/app/token` with an
   e-mail and password, or with a single-use pairing code a signed-in member created on the core's
   Settings, Glasses page, plus the app's install id (`device_id`) and a `device_model` label. The
   core answers a core access token (EdDSA, published keys at `GET /v1/core/jwks.json`), a device
   ("wearable") token bound to that install id, the user and the capabilities. 401
   `invalid_credentials`, 403 `pairing_required` (strict sign-in), 429 `too_many_attempts` are shown
   to the person in words.
2. The app exchanges the core access token at Field: `POST /v1/auth/exchange` (field-api). Field
   verifies it against the core's JWKS (`FIELD_CORE_JWKS_URL`; re-read once on an unknown key id or a
   failed signature), checks the core device status (2.2), maps the token's core role keys to Field
   roles (`FIELD_CORE_ROLE_MAP`, laid over a default table; a token whose roles map to nothing gets
   403 `FIELD-AUTH-403-NO-FIELD-ROLE` with a sentence for the sign-in screen) and issues a Field
   token for at most 600 s (never longer than the core token). The core's permissions are echoed as
   `core_permissions`; Field decides nothing on them.

3. The hosted field console (M5-J01) signs in the same way from its own server: the browser sends
   e-mail + password to the console (`POST /api/console-auth/signin`), the console calls the core's
   app token with `X-Requested-With: lr`, a per-browser `device_id` `web-console:<uuid>` and
   `device_model` `WEB_CONSOLE`, then `/v1/auth/exchange` with `client_id: field-console` and no
   `device_id`. Field answers such a token without a device binding (a browser is not a field device;
   no field.device, no device status); a token bound to any other device id keeps the checks of 2.2.
   Both tokens stay in httpOnly cookies on the console's host (`FIELD_CONSOLE_CORE_URL`).

### 2.2 Device status and revocation

`FIELD_CORE_DEVICE_STATUS_URL` is a template such as
`{core}/v1/core/devices/{device_id}/status?tenant_id={tenant_id}` (the tenant comes from the
token). Field asks it on every exchange about the core-bound device id. Only `active` lets the
exchange through; an unknown device, one in another organisation, an unreachable core or a
malformed answer count as not active (fail closed). Revoking the device in the core
(`DELETE /v1/wearable/sessions/{id}`, or Settings, Glasses in the core's web app) makes the next
exchange answer 403.

### 2.3 Decisions on the phone and the glasses

The app's decision flow (module `apps/field-android/feature-decisions`, ported from the core's
former wearable app) calls the core directly with `Authorization: Bearer <device token>` and
`X-Device-Id`:

| Call | What for |
|---|---|
| `GET /v1/wearable/next` | The decision waiting longest for this approver (`item: null` when none). |
| `GET /v1/briefs/decision/{id}?format=spoken\|card` | The core's template brief (about 20 s spoken; a card of at most 240 characters). |
| `POST /v1/briefs/decision/{id}/check` `{"text"}` | The core's number check: `{accepted, reasons[], template_text}`. |
| `POST /v1/voice/challenges`, `POST /v1/voice/commands` | A single-use challenge, then the voice turns ("approve option two", "reject", "repeat"), the read-back and the mandatory confirm turn. The core's grammar decides every intent. |
| `GET` / `POST /v1/auth/step-up` | A band's second factor, typed on the phone. |
| `POST /v1/evidence/photos` | A photo attached to a recovery plan (multipart, with consent). |
| `GET /v1/wearable/sessions`, `DELETE /v1/wearable/sessions/{id}` | The member's devices, and revoking one. |

Field adds one step of its own: `POST /v1/briefs/spoken` on field-api (`X-Core-Token` = the device
token, forwarded and never stored; `X-Device-Id`) asks the Meta model router to rewrite the
template into a spoken brief, sends the rewrite to the core's number check, and answers the
template whenever the check refuses, the model is off or anything fails. The app speaks the
template after 8 s without an answer. Approvals, permissions and whether a step-up is needed are
decided by the core alone; Field only carries the words.

### 2.4 The goods receipt: two signed feed rows

When a goods receipt (movement 101) posts in the ERP, the field-worker reads the posted material
document and the on-hand after it from the ERP (through `ErpReadPort`, never computed) and stages
two deliveries, one per feed, idempotent on the ERP event id:

- **inventory feed** (`FIELD_CORE_INVENTORY_FEED_URL`, `FIELD_CORE_INVENTORY_FEED_SECRET`): per item
  and location `{"item_code", "location_code", "as_of", "on_hand_qty"}`, the absolute on-hand after
  the receipt;
- **open-supply feed** (`FIELD_CORE_SUPPLY_FEED_URL`, `FIELD_CORE_SUPPLY_FEED_SECRET`): per PO and
  item `{"kind": "PO", "ref", "item_code", "location_code", "qty", "due_date", "status":
  "received"}`, where `ref` is the PO number exactly as the core knows it (for example
  `PO-26-1001`, never `<PO>-<item>`) and `qty` the quantity received. A receipt without a PO
  reference sends the stock row only.

Rules, as agreed with the core:

- **Body:** exactly `{"rows": [...]}`; the bytes sent are the bytes signed.
- **Signature:** `X-SCMTIPS-Timestamp` (Unix seconds, within 5 minutes of the core's clock) and
  `X-SCMTIPS-Signature: sha256=<hex HMAC-SHA256(secret, timestamp + "." + raw body)>`, with the
  feed's own secret, which the core shows once when the feed is created. A fresh timestamp on every
  try, the same body. Field also sends `Idempotency-Key: <event_id>:<feed>` for its own logs (the
  core does not use it).
- **409 counts as delivered.** The core refuses the same body twice within ten minutes with 409
  `duplicate`, so a 409 means the core already has these rows; it is never retried.
- **Permanent refusals** (400, 413, 415, 422) are dead at once. Anything else (network error, 401,
  404, 429, 5xx) is retried with exponential backoff and jitter up to
  `FIELD_CORE_FEED_MAX_ATTEMPTS`, then dead. Dead deliveries stay in `field.core_feed_delivery` for
  an operator.
- **Ordering:** deliveries go in staging order, which is the order the ERP was read. Stock rows are
  upserts, so before a delivery is sent every row for which a newer delivery of the same key was
  already delivered is dropped (key: item and location for stock; kind, ref and item for open
  supply), and a delivery left empty is marked `skipped` (`superseded`). A late retry never
  overwrites a newer on-hand or reopens a line a newer receipt closed.
- **Sandbox receipts** are never sent unless `FIELD_CORE_FEED_SANDBOX` is on. Nothing is sent
  unless both feed URLs are set.
- **Codes:** the core's own codes. When the ERP uses other codes, `FIELD_CORE_CODE_MAP` maps
  materials, plants and PO numbers; an unmapped PO number is sent unchanged and logged.

### 2.5 The ERP snapshot (`erp_extract`: inventory and open supply)

Every `FIELD_CORE_SNAPSHOT_INTERVAL_S` seconds (first at start-up; 0 = off; off whenever a feed
URL is unset) the field-worker reads the stock and the open purchase-order lines of the plants of
the active production sites (of the tenants in `FIELD_CORE_SNAPSHOT_TENANTS`, empty = all; never a
plant a sandbox site uses) and stages only the rows that changed since they were last staged
(`FIELD_CORE_SNAPSHOT_RESEND_H`), at most `FIELD_CORE_SNAPSHOT_BATCH` rows per delivery. Open lines
go with the open quantity, the ERP's status and due date, `supplier_code` and `lane_code`; a fully
received line goes as `received`. Delivery, signing, 409 and ordering are those of 2.4: receipts
and snapshot rows share one staging order. A key that two ERP plants would produce for one core
location is sent by neither (logged as a conflict). The snapshot makes the ERP the system of record
for these two tables at the core.

### 2.6 The core's drone-world export and site pack

The core writes the SAMPLE drone-OEM world for each connected system
(`uv run scmtips-sample-exports write` in the core repository): `samples/exports/erp-sim/`
(plants, storage locations, materials with units and barcode = code, suppliers, stock, the open
PO lines, `manifest.json`) and `samples/exports/field-site-pack/` (sites, bins, labels).
`uv run python -m tools.dev_stack.stack seed-core-export <core>/samples/exports/erp-sim` loads the
ERP part into erp-sim with the core's own codes (one ASN per open PO, so a receipt can be
captured against it) and creates the site pack's Field sites through field-api, so the GR flow
needs no code map for this world. A missing folder is a clear failure, not a silent skip.

### 2.7 File-mode fallbacks the core offers

Every message has a file form with the same columns (the templates in
[`templates/`](integration/exchange-contract-v1/templates/), also served by the core at
`GET /v1/exchange/messages/{key}/template`). The core reads a file into the same message and
checks it with the same rules; file rows are labelled SIMULATED.

- `POST /v1/exchange/messages/{key}/validate` (JSON) and `/validate-file` (XLSX or CSV) answer how
  the core reads a message (envelope, rows, errors by row and column) and store nothing.
- The feeds also take a file body (`Content-Type: text/csv` or the XLSX type), signed the same way.
- The core's data import (`POST /v1/imports`) takes the `erp_extract` tables.
- At the core's head after 31 Oct, a file upload for `goods_receipt`, `erp_extract`, `signal` and
  `progress` exists (`POST /v1/exchange/messages/{key}/import-file`; the pinned README of 31 Oct
  still lists these as "being built", see section 4).

Field itself produces no files today: when the feeds are down its deliveries wait, retry and, at
the end, stay dead for an operator. An operator can always fill the `goods_receipt` template from
the ERP and upload it in the core.

## 4. Versioning

- Field is pinned to **`scmtips.exchange/v1`**. Every message says `"contract":
  "scmtips.exchange/v1"`, and the schemas' `$id` is `urn:scmtips:exchange:v1:<message>`.
- [`docs/integration/exchange-contract-v1/`](integration/exchange-contract-v1/) is **byte-identical
  to the core's export of 31 Oct 2026** (its README: generated 2026-10-31T09:32:41Z; 33 files).
  Do not edit it by hand; a new copy comes from the core's
  `python -m lr_api.domain.exchange.export <dir>`.
- Checked on 1 Nov 2026 against the core's the core's integration branch head: a fresh export has the same
  schemas, examples, CSV templates and `contract.json` byte for byte, and the same XLSX sheets
  (only the workbook's creation time in `docProps/core.xml` differs). Only the README's "what
  SCMTIPS does today" lines are newer (the file uploads of section 2.7, and the planning legs
  parked). v1 itself has not changed.
- A breaking change would be `scmtips.exchange/v2`, in its own folder, next to v1. The core's own
  app APIs of section 2 are versioned by the core's OpenAPI (`/v1`), not by this contract.
